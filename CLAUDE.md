# LiteraryWorm: project guide for Claude Code

LiteraryWorm is a reading and listening app (ebooks and audiobooks, household profiles). It lives at https://www.literaryworm.com (Vercel; `literaryworm.com` redirects there). The assessment brief is `README.md`; the product blueprint is `front_end/user_journey.md`; stories are in `user_stories.md`.

## Where things are

- `front_end/literaryworm_app/`: the React app (see its `README.md` for routes and layout). Vercel's Root Directory is this folder, so its `vercel.json` (the rewrite that lets every route survive a refresh) lives here too.
- `front_end/BookWorm_web_app_wireframe/`: the Figma Make wireframe. Visual source of truth; don't edit.
- `front_end/style_guide.md`: design tokens, type, components, motion, voice.
- `supabase/`: migrations, Edge Functions (`books`, `manage-profile`, `checkout`, `manage-account`, `stripe-webhook`, `release-emails`, `club-invite`, `author-news`, `dictionary`, `characters`, `whats-new`, `kids-report`, `club-meetings`, `club-digest`, `gift-reminders`, `club-calendar`, `unsubscribe`, `summaries`, `ask`), Auth email templates (`templates/`), security tests. See `supabase/README.md`. Project: `literaryworm` (ref `ldzdmrdvmacpudsbngvd`). The app is deployed on Vercel at `https://www.literaryworm.com`; `https://www.literaryworm.com`, `https://literaryworm.com` and `http://localhost:5173` must all be in the `ALLOWED_ORIGINS` function setting, or the browser blocks the functions' answers and the app reports "offline".
- `schema.sql`: generated from the migrations by `supabase/build-schema.sh`; don't edit by hand. `drawsql.png` is its ERD, rendered from `docs/erd/erd.html`.
- `prompt.md`: the build brief and phase plan.
- `vite-project/`: an unrelated earlier scaffold. Don't use it.

## Commands (run in `front_end/literaryworm_app`)

```bash
npm run dev     # http://localhost:5173
npm run build   # tsc -b + vite build; must pass before every commit
npm run lint    # oxlint; must be clean
npm test        # Jest unit tests (src/lib/*.test.ts); must pass before every commit
npm run test:e2e  # Jest + Playwright smoke tests (e2e/*.e2e.ts) on the demo; must pass before every commit
```

## Conventions

- TypeScript strict. React Router DOM, declarative routes with `BrowserRouter`; routes live in `src/App.tsx`.
- **State is in memory only** (`src/store`). No `localStorage`, with two exceptions: the Supabase session (`src/lib/supabase.ts`, key `literaryworm-session`) so a member stays signed in, and which device this browser is (`src/lib/deviceId.ts`, key `literaryworm-device`: a random id and the account id, removed at sign-out) so a refresh isn't a new device. (Termly's consent banner keeps its own `TERMLY_API_CACHE` entry.) Everything else resets on refresh on purpose.
- **Real accounts go through `src/lib/accountApi.ts`** (Supabase Auth, `library_items`, `logs`, the `checkout` function) and `src/lib/useAuthSync.ts` (restores the session, follows sign-in and sign-out). Use `useLibrary()` for the library: it writes to Supabase first, then updates the store. The demo household stays in memory and never calls Supabase.
- **Book lists go through `src/lib/booksApi.ts`**, which calls only the `books` Edge Function. Never fetch Google Books from the browser. Kids profiles use the sample catalog only.
- **Public logs come from `src/lib/logsApi.ts`** (the `logs` table with the publishable key, embedding only `profiles.display_name`). Public pages never read `library_items`.
- **Reading progress and bookmarks go through `src/lib/useReading.ts`.** Opening a book adds it to the library as Reading; the place is dispatched straight away and saved to Supabase (`reading_progress`) a moment later, so reading never waits for the network; bookmarks save first, then show. Real accounts keep them in `state.accountReading`, in-memory accounts in `ProfileData`; `activeReading()` picks the right one. Positions are fractions of the whole book (`src/lib/reading.ts`), shared by the reader and the player.
- **Household profiles go through `src/lib/useProfiles.ts`.** Real accounts save name, avatar and genres to `reader_profiles` directly; Kids profiles, PINs, limits, age ratings and deletes through the `manage-profile` function (which re-checks the password); PINs are verified on the server. After a change the profiles are read back (`setProfiles`). A real profile has `hasPin`, never the PIN.
- **Account changes go through `src/lib/useAccount.ts`**: membership (pause, resume, cancel, restart) and deleting through the `manage-account` function; display name and marketing emails straight to their tables; Download my data builds a JSON file in the browser.
- **Highlights and notes go through `src/lib/useHighlights.ts`**, like bookmarks: real accounts save to `highlights` first, then show; in-memory accounts keep them in `ProfileData`. A highlight is found by chapter, page and character offsets in the page's text (`src/lib/highlights.ts`).
- **Authors and narrators** have pages at `/authors/:name` and `/narrators/:name` (`pages/Person.tsx`, helpers in `lib/people.ts`), keyed by the name shown on the book; link to them with `personPath()`. An author's Google Books titles come from the `books` function's `author` mode. Following goes through `lib/useFollows.ts` (per profile, `follows`, saved first like favourites; loaded with the collections); Home's *New from people you follow* row uses `fromFollowed()`; My Library → *Following* lists them (`components/FollowingView.tsx`). A person's page shows how many profiles follow them from the `follower_count()` RPC (`lib/followersApi.ts`, a count, never who; visitors too), and an author search's *Authors* cards from `follower_counts()` (`fetchFollowerCounts()`, one call for the list, at most 50 names; `followersShort()`). Home's *Most-followed authors* (`components/MostFollowed.tsx`, not Kids) reads `most_followed()` (`fetchMostFollowed()`: names with two or more followers, counts only).
- **Remind me** (`components/RemindMe.tsx` on the book page, `lib/useReminders.ts`, dates in `lib/release.ts`): per profile in `release_reminders` (saved first, loaded with the collections), only for books whose release day is still to come and only when Google gives the exact day. Once the day passes, `components/RemindersView.tsx` shows it on Home (*Out now*) until dismissed, and in My Library → Reminders. Members also get an email that day (see Email) unless they turned it off in Account → Preferences (`account_private.release_emails`, `setReleaseEmails()`).
- **The notification bell** (`components/NotificationBell.tsx` in the header, `lib/useNotifications.ts`, counting in `lib/notifications.ts`): released reminders newer than `ProfileData.notificationsSeenAt`, plus unread club posts up to the reader's chapter (`spoilerFreeUpTo()`; clubs with alerts on; never Kids profiles). Opening it marks the profile seen: members through `mark_notifications_seen()` (the database's time, so every device agrees), the demo in memory. Club posts keep their own read state (`club_members.last_read_at`). New kinds of notification get a count in `bellCount()` and a group in the panel; one with a start time goes in its `alerts` (new until the bell is opened after it), like the goal and streak alerts (`goalAlerts()` in `lib/goals.ts`), the yearly renewal reminder and the yearly offer (`yearlyOffer()` in `lib/billing.ts`: monthly members billed through Stripe, for 30 days from 11 months after `Account.memberSince`, which is `subscriptions.created_at`).
- **Favourites, ratings, custom lists and recent searches go through `src/lib/useCollections.ts`.** They belong to the active profile (`ProfileData`); real accounts save to `favorites`, `book_ratings`, `custom_lists`, `custom_list_items` and `reader_profiles.recent_searches` first, then dispatch (recent searches save in the background). `useAuthSync` loads every profile's collections after the profiles. Shared lists are read with the `shared_list` RPC (`src/lib/sharedListApi.ts`), never the tables.
- **Definitions come from `src/lib/dictionaryApi.ts`**, which calls only the `dictionary` Edge Function (the Free Dictionary API is asked on the server).
- **Audiobook playback lives in `src/components/PlaybackProvider.tsx`** (read it with `usePlayback()` from `src/lib/playback.ts`), above the routes, so a book keeps playing in the mini-player (`src/components/MiniPlayer.tsx`) while the member browses. The player page is a view of it. Opening the reader pauses it; switching profile or signing out stops it, and its last save still goes to the profile that was listening (`saveProgress` / `addTimeUsed` take a `profileId`).
- **The player page and the mini-player have the same controls**, from `usePlayerControls()` (`src/lib/usePlayerControls.ts`; where each control goes is worked out in `src/lib/playerNav.ts`) and the shared pieces in `src/components/PlayerControls.tsx` (volume, *Go to*, player settings, *Listen on another device*, the handoff prompt). Add a control to both. Speed, volume, mute, skip lengths and intro and outro skipping are `ProfileData.player`, changed through `usePlayerSettings()`, which saves members' settings to `reader_profiles` in the background; the engine applies them (narrators have `setVolume`).
- **Listen on another device** is for members: `src/lib/useDeviceLink.ts` registers this browser as a `listening_devices` row (one per browser, the id kept by `deviceIdFor()`) (checking in through `touch_listening_device()`), and `src/lib/devicesApi.ts` sends and hears `playback_handoffs` (Supabase Realtime, plus a check when the tab comes back). It reaches the views as `usePlayback().link`; `open(book, { at, autoplay })` opens a book at a place.
- **Lock screen:** `components/MediaSession.tsx` (above the routes) puts the open book in the Media Session API with the same actions as the mini-player; artwork is drawn by `lib/coverArt.ts` (also used by quote cards, `lib/quoteCard.ts`). **Install:** `public/manifest.webmanifest` and `public/icons`; `lib/installApp.ts` keeps the browser's install offer (imported first in `main.tsx`).
- **Stats** (`lib/stats.ts`, My Library → Stats) come from `ProfileData.readingDays`: `listened` is the listening part of `seconds`, `books` the ids finished that day. Members save both through `record_reading(profile, day, minutes, finished, listening_minutes, volume_id)` (`reading_days.listening_minutes`, `finished_books`). Pass `listening` to `useDailyLimit` for player time and the book id to `finishedBook`. *Share as a picture* draws the year as a card (`lib/yearCard.ts`, `components/YearCardDialog.tsx`); it and the quote card share `components/ShareImage.tsx` (look, preview, Share, Download, Copy), and both are drawn in the browser, never uploaded.
- **Recommendations** are worked out in the browser (`lib/recommend.ts`) from a profile's finished books, ratings and favourites; only catalog titles the profile may see, never books in its library.
- **Club notifications and listen along** use Supabase Realtime: `components/ClubAlerts.tsx` listens to `club_posts` once and passes posts on through `lib/clubEvents.ts`; `components/ListenAlong.tsx` keeps playback and `club_listening` in step for the session in `lib/listenAlong.ts`. Never alert about, or count, posts past the reader's chapter (`spoilerFreeUpTo()` in `lib/clubs.ts`). Give every Realtime channel its own name (channels sharing one close together).
- **Billing is Stripe** (`supabase/functions/_shared/stripe.ts`): a new membership is paid on Stripe Checkout (hosted, so card details never reach us); `checkout` returns its url and only the `stripe-webhook` function writes a paid membership, mapping events to accounts through `stripe_customers` and handling each once (`stripe_events`). Prices are found by lookup key (`literaryworm_<plan>_monthly`, and `literaryworm_<plan>_yearly` at ten times as much): Basic $9.99, Standard $14.99, Premium $24.99 a month. To change a price, create a new Stripe price on the same product that takes over the lookup key (`transfer_lookup_key`) and archive the old one (running memberships keep it; the Terms promise notice before a member's price changes), then change `data/plans.ts`, `PRICES` in `checkout/index.ts` and `public.plans` (a migration) together, and rewrite the description and structured data in `index.html` from `lib/seo.ts` (what Google shows: prices in the description and each plan's monthly and yearly Offer; `seo.test.ts` fails until they match). `public/sitemap.xml` lists the public pages. **Yearly billing** (`subscriptions.billing_interval`, from the price's lookup key; `Account.billingInterval`, `renewsAt`): a year starts the day it's paid for; monthly to yearly switches in place (`billing_cycle_anchor: { type: "now" }`, an object since API version 2026-09-30, the unused month credited), yearly moves up at once (the difference charged) and down at renewal, and to monthly at renewal through a Stripe subscription schedule (`scheduleMonthly()` in `_shared/stripe.ts`: the year as it is, then the monthly price; the schedule's phase sets the subscription's `switch_to_monthly` metadata, which `subscriptionRow()` reports as `subscriptions.switch_to_monthly` only while the schedule is attached; choosing yearly again or cancelling calls `releaseSchedule()`, and anything that cancels a Stripe subscription must release its schedule first); yearly memberships can't pause or move their billing day; a late cancel ends a year on; the bell reminds 30 days before renewal (`renewalReminder()` in `lib/billing.ts`, which the Terms promise). Pause, cancel, billing day and the payment method (Customer Portal) go through `manage-account`, which changes Stripe first. **Cancelling needs 48 hours' notice** to stop the next charge (`cancellationEnd()` in `_shared/stripe.ts` and `lib/billing.ts`, the same rule): later than that, Stripe's `cancel_at` is set a period on and the membership ends after one more charge; `subscriptions.cancel_at` is when an ending membership ends (the webhook keeps it from Stripe). No refunds. Keep the Terms, the Return Policy, the Plans renewal terms and Account's billing section saying so. Billing history and promo codes (`components/BillingHistory.tsx`) also go through `manage-account` (`billing_history`, `promo_code`): read from Stripe each time, never copied to the database; Checkout allows promotion codes. Receipt links are Stripe's hosted invoice pages. **Gift memberships** (`pages/Gifts.tsx` at `/gifts`, `components/RedeemGift.tsx` in Account, Plans and Gifts, `lib/gifts.ts`): `checkout` with `{ gift: true, planId, months, startsOn? }` opens a one-off Checkout (the plan's own product and monthly price × months, or its yearly price for 12 months, two months free, as `giftPriceCents()` in `lib/gifts.ts` shows; so it's taxed like the membership; no `custom_text`, which Stripe Managed Payments refuses); `stripe-webhook` makes the code in `gift_codes` once per session (with `starts_on` from the session's metadata: a gift bought for a later day, up to a year ahead, `parseGiftStart()`; it can't be redeemed before that day starts anywhere, `giftStarted()`; the buyer is emailed three days before a later start by the `gift-reminders` function, hourly pg_cron, `claim_gift_start_reminders()`, `gift_codes.reminded_at`, never with the code; or, when the buyer gave `recipientEmail` (and an optional `message`, `GIFT_MESSAGE_MAX`), the same function emails the code to that person once it can be redeemed, `claim_gift_deliveries()`, `delivered_at`, and then clears the address and message, and there's no buyer reminder); `manage-account` `gift` redeems it once (claim first, released only if Stripe fails): on a membership on the same plan the next charge moves back (`trial_end`), without one Stripe starts a subscription free until then that cancels if no card is added, carrying `gift_consent_at`, and the webhook writes the membership from that consent. `subscriptions.gift_until` (from the subscription's metadata) shows in Account and blocks billing-day moves. Never send Stripe's ids to the browser (`subscriptions.stripe_linked` says whether a card is on file), never pass `payment_method_types`, and keep keys in function secrets (`STRIPE_SECRET_KEY`, a restricted `rk_` key, and `STRIPE_WEBHOOK_SECRET`).
- **Staff are never billed.** Everyone with a staff role (Admin, Editor, Developer, Billing, Customer service, Blog, Sales) has a complimentary membership for as long as they hold one (`subscriptions.complimentary`, set only by a database trigger from `staff_roles`: Premium, active, no billing day, no renewal, no Stripe subscription; granting a first role starts it, removing the last ends it, moving between roles keeps it; migration 3601). `checkout` refuses staff, `manage-account` won't pause or cancel a complimentary membership, `stripe-webhook` cancels any Stripe subscription that reaches a member of staff (and deletes its draft renewal), and Account, Plans, Gifts and Team access say so. Never create a Checkout Session or subscription for staff; check any staff role (`isStaff`), not just admin.
- **Staff roles** (`lib/staff.ts`, `lib/staffApi.ts`, `useStaffRoles()`): admin, editor, developer, billing, customer_service, blog, sales; admins can do everything; every role comes with a complimentary membership (`hasRole()`, and `has_staff_role()` in the database). Only admins grant or remove roles, through `grant_staff_role()` / `revoke_staff_role()` (an email without an account is invited, `staff_invites`); never write `staff_roles` from the browser. Gate any new staff tool on a role in RLS, not just in the UI. The staff dashboard (`/dashboard`, `pages/Dashboard.tsx`, lazy-loaded) is for billing staff and admins; it reads only `staff_dashboard()`, a security-definer function that returns totals, never who. Member lookup (`/support`, `pages/Support.tsx`, lazy-loaded, linked from Team access) is for customer service and admins: `support_member_lookup(email)` returns one member's plan and billing state, profile counts, this month's listening and offline devices (never library, reading, notes or Stripe ids), records each lookup in `support_lookups` (admins read it; kept a year) and allows 60 an hour. Keep the Privacy Policy's *Our support team* paragraph true to what it returns.
- **Uploaded books** (`lib/epub.ts` reads the EPUB; `lib/useUploads.ts`, `lib/uploadsApi.ts`): the text goes to the private `user-books` bucket at `<user_id>/<id>.json`, listed in `uploaded_books`; ids are `u-` and 32 hex digits, valid volume ids. Use `useUploadedBook(id)` (they aren't in `getBook()`). Opened uploads are kept on the device in the `lw-uploads` cache (`lib/uploadCache.ts`), cleared on delete and at sign-out. Deleting a profile or account must also remove its files (`manage-profile`, `manage-account`).
- **Who reads an audiobook is a narrator (`src/lib/narration.ts`)** that the engine drives: the book's LibriVox recording (`book.recording`, from `src/data/librivox.ts`, generated by `scripts/build-librivox.py`; MP3s streamed from the Internet Archive) or a device voice (Web Speech API) reading the text. The 571 public-domain titles have a recording and full Project Gutenberg text (`public/texts/<id>.json`, built by `scripts/build-texts.py` to line up with the recording's chapters); other titles have only sample text. The profile's choice is `ProfileData.narrationVoice` (in memory; speed is saved with the player settings); `resolveNarration()` picks the recording by default, else a British English voice. Don't edit the generated files by hand. A new title needs a `PROJECTS` entry in `build-librivox.py` and a `BOOKS` entry in `build-texts.py` (its heading pattern, or `proportional` with `"heading": None` where the edition's chapters don't match the tracks; `start` and `end` cut contents lists and back matter; `"trim": True` cuts Gutenberg's closing lines, notes, indexes and publishers' lists, `"trim": 2` also glossaries and anything after the book's own last THE END, and must not be used where footnote blocks follow chapters); run `build-texts.py <id>` for the new ids only, so existing texts (and saved highlights) never change, then `scripts/upload-texts.sh <id>`.
- **Book summaries come from `src/lib/summaryApi.ts`**, which calls only the `summaries` Edge Function. Claude (`claude-haiku-5-5`, using the `ANTHROPIC_API_KEY` function setting) writes a book's short and detailed summaries the first time anyone asks; the function keeps them in `book_summaries` (service role only, no browser access) and limits new ones per IP and per day. The book page and each My Library row (*Summary*, in a dialog) show them to members and the demo, labelled as written by AI. The function's catalog list (`supabase/functions/_shared/catalog.ts`) must stay in step with `src/data/books.ts`.
- **Ask the book (`src/lib/askApi.ts`, `components/AskDialog.tsx`)** calls only the `ask` Edge Function, which sends Claude (`claude-haiku-5-5`) the public-domain text up to the reader's chapter (fetched from the site's `/texts`, the last ~120,000 characters) and tells it never to reveal later events. Public-domain titles only; rate limited per IP and per day.
- **Who's who (`src/lib/charactersApi.ts`, `components/CharactersDialog.tsx` in the reader)** calls only the `characters` Edge Function, which sends Claude (`claude-haiku-5-5`, structured output) the public-domain text up to the reader's chapter (`_shared/bookText.ts`, shared with `ask`), drops anyone first met later (`checkCharacters()`), and keeps each book-and-chapter list in `book_characters` (service role only), returning the kept one so every reader sees the same list. The browser filters by chapter again. Public-domain titles only, not Kids profiles; new lists rate limited per IP and per day.
- **What's new** (`pages/WhatsNew.tsx` at `/whats-new`, first in the footer, and linked from the public home page, members' Home and Plans by `components/WhatsNewLink.tsx` (naming the newest major change) and from Account → Help; `lib/changelog.ts`, `lib/changelogApi.ts`; filters: Everything, What's new (the last 30 days, `NEW_DAYS`), Major, Minor, New features, Updates, Fixes; built-in copy in `src/data/changelog.json`, seeded by migration 3902): public; editors, developers and admins write it in place (`changelog_entries`, RLS through `has_staff_role()`). Add an entry for every user-facing change, and mark the big ones *major*. **Kids reading report:** Account → Family shows each Kids profile's last 7 days (`kidWeek()` in `lib/kidsReport.ts`) and its weekly goal (`reader_profiles.weekly_goal_minutes`, `Profile.weeklyGoalMinutes`: for a Kids profile set by a grown-up in the profile editor through `manage-profile` `set_weekly_goal` with the account password, never from the browser (a trigger refuses the browser's role); grown-up and teen profiles set their own in Goals, saved straight to the column (`setWeeklyGoal()` in `useGoals`); progress from `weeklyGoal()`, also the *Weekly goal* card in the child's Goals and a line in the email; the report groups Kids profiles by how the week went, `kidGroup()` / `groupKids()` in `lib/kidsReport.ts` and the same in `kids-report/email.ts`, with headings only when there's more than one group); members who turn on `account_private.kids_report_emails` (`setKidsReportEmails()`) get last week's on Monday mornings from the `kids-report` function (pg_cron, `claim_kids_report_emails()`, `kids_report_week()`, `kids_report_sends`). On the 1st to the 3rd of each month pg_cron calls the `whats-new` function, which emails last month's major entries once (`whats_new_sends`) to members who turned on `account_private.update_emails` (off by default, `setUpdateEmails()`). Every email has a one-click unsubscribe (`_shared/unsubscribe.ts`: account id + HMAC with the Vault key; `List-Unsubscribe-Post`) handled by the `unsubscribe` function and the `/unsubscribe` page, which asks first; `l=` names the email it turns off (`whats-new` by default, `kids-report`, `club-meetings`, `club-posts`). **Club posts by email:** members who turn on `account_private.club_post_emails` (off by default, `setClubPostEmails()`; turning it on starts from that moment) get one email a day from the `club-digest` function (pg_cron 17:00 UTC, `claim_club_post_digests()`, `account_private.club_posts_emailed_through`): new posts by other members since they last opened the club, in clubs with alerts on, only about chapters the account has reached (`reading_progress`, the same rule as `spoilerFreeUpTo()`), giving the club, chapter, count and who wrote them, never the text.
- **Goals and streaks** live in `ProfileData.readingGoals` / `readingDays` (per profile, like favourites). Reading time comes from `useDailyLimit`; members' minutes go to Supabase through `record_reading()` (`src/lib/readingActivity.ts`, whole minutes, retried); finished books are counted in `useReading` and `useLibrary`. Streaks and month summaries are worked out in `src/lib/goals.ts`. If the goal tables can't load, the account still opens.
- **Household challenges** (`lib/challenges.ts` for the rules and progress, `lib/challengesApi.ts`, `lib/useChallenges.ts`, `components/ChallengesView.tsx` in Goals): per account (`household_challenges`, `challenge_participants`, owner-only RLS, up to 20); any profile, Kids included, starts, joins or leaves one; progress is worked out in the browser from each profile's `readingDays`, never stored. Only the profile that started one sees *Delete*. The demo keeps a sample challenge in memory, like its book club. `challengeError()` mirrors the table's checks.
- **Import from Goodreads or StoryGraph** (`lib/importCsv.ts` reads and matches, `components/ImportDialog.tsx` in My Library): the CSV is read in the browser and never uploaded; books are matched to the catalog, then looked up through `fetchBookPage()` (the `books` function, spaced about a second apart for its 60-a-minute limit) and accepted only when `sameBook()` agrees on title and author. Imported books are added with `useLibrary().add(entry, status, { countFinished: false })`, so old reads never count towards today's goal or stats. Not for Kids profiles.
- **Book clubs** are per account (`book_clubs`, `club_members`, `club_posts`), reached through `src/lib/useClubs.ts`: Supabase for members (`clubsApi.ts`; joining only through `join_club()`), an in-memory sample club for the demo. Not offered to Kids profiles. Posts past the reader's place stay hidden until they choose to see them. **Meetings** (`club_meetings`, `lib/clubCalendar.ts`, *Meetings* on the club page): only the club's owner schedules, changes (`updateMeeting()`) or cancels them (RLS); members see them with *Add to calendar* (`meetingIcs()`, made in the browser, never uploaded) and get an email the day before from the `club-meetings` function (pg_cron every 10 minutes, `claim_club_meeting_reminders()`, the owner's `time_zone`), unless `account_private.club_meeting_emails` is off (`setClubMeetingEmails()`) or they answered *Can't make it*. Members can subscribe in a calendar app (*Subscribe in your calendar*, `calendarFeedUrl()`): the `club-calendar` function signs a link per member and club (HMAC with `club_calendar_secret` in Vault, nothing stored) and serves the club's meetings as `.ics` with the same UIDs, checking membership on each read. Moving or cancelling an upcoming meeting is noted by triggers in `club_meeting_changes` (service role only; one note per meeting until sent; not when the club itself is deleted) and the same function emails the other members (`claim_club_meeting_changes()`, `meetingChangeEmail()`), under the same switch, with the meeting as a calendar file (`meetingChangeIcs()`: the same UID as `meetingIcs()`, `SEQUENCE` in minutes since 1970 in both so the newest file wins, `METHOD:CANCEL` when cancelled; sent as a Mailgun attachment). **RSVPs** (`club_meeting_rsvps`, read by the club's members): written only through `answer_club_meeting()` (`answerMeeting()`); meetings in the next day show in the bell (`meetingAlerts()`, `soonMeetings()`), not for members who can't make it. **Invites by email**: the club page's *Invite by email* calls the `club-invite` function (`inviteByEmail()` in `clubsApi.ts`, members only), which checks membership and limits in `record_club_invite()` and keeps only a sha256 fingerprint of the address in `club_invites` (30 days, cleaned by pg_cron), never the address; the email links to `/clubs/join/:code` (`pages/JoinClub.tsx`), which joins after signing in.
- **Across devices:** `useReadingSync` reloads progress, bookmarks and highlights when a member comes back to the tab (after 15 s away) or back online; `useReading` saves the place as soon as the tab is hidden. An open reader offers to go to a place saved on another device.
- **Plan limits** (`lib/planLimits.ts`, numbers from `data/plans.ts` and `public.plans`): profiles (Basic 1, Standard 5, Premium 12; `MAX_PROFILES` and the database's profile trigger cap them at 12) and audiobook hours a month for the whole account (Basic 5, Standard 30, Premium unlimited) through `lib/useListeningAllowance.ts`, which the playback engine uses to pause (`Playback.allowance`); members' other devices count through `listening_minutes_between()`. ## Phase workflow

Build in phases (see `prompt.md`). At the end of each phase:

1. `npm run build`, `npm run lint`, `npm test` and `npm run test:e2e` clean (GitHub Actions runs all four on every push to `main`, `.github/workflows/ci.yml`). A new page or flow gets a smoke test in `e2e/smoke.e2e.ts`. New logic in `src/lib` gets tests beside it (`*.test.ts`). The paging snapshots in `src/lib/__snapshots__` must not change unless paging is meant to (saved highlights depend on it).
2. Playwright screenshots at 1440px and 390px, compared against the wireframe; save keepers to `front_end/literaryworm_app/docs/screenshots/`.
3. Chrome DevTools: no console errors; Lighthouse accessibility 100.
4. Update `schema.sql` and re-render `drawsql.png` for any new data.
5. Update the docs (app README phase table, `user_stories.md` build status, `user_journey.md` build notes, root `README.md` project status).
6. Commit only the files for that work, push to `main`, and stop for the user's review.

## Rules that must not be broken

- Never commit secrets. `.env*` files stay local; only `.env.example` (no real values) is shared. Never put a secret in a `VITE_` variable.
- The browser must never call Google Books directly (backend phases: go through a Supabase Edge Function).
- Don't edit, delete or rewrite anything in `prompt-records/` or the hooks in `.claude/hooks/`.
- Every Supabase table has Row Level Security enabled, with `(select auth.uid())` policies and column-level grants. Index every foreign key, with `CREATE INDEX CONCURRENTLY` in its own one-statement migration (the MCP `apply_migration` runs in a transaction, so apply those with `execute_sql`).
- Edge Functions validate every input, use the CORS allowlist in `_shared/cors.ts`, and return `{ error: { code, message } }`. Test (`deno check`, `deno test`) before deploying.
- `DELETE` statements always have a `WHERE` clause (a hook blocks the rest).
- Don't stage unrelated files (`.cto-toolkit/`, tool folders like `.windsurf/`, `prompt-records/` edits made by hooks) in feature commits.
