# LiteraryWorm: project guide for Claude Code

LiteraryWorm is a reading and listening app (ebooks and audiobooks, household profiles). It lives at https://www.literaryworm.com (Vercel; `literaryworm.com` redirects there). The assessment brief is `README.md`; the product blueprint is `front_end/user_journey.md`; stories are in `user_stories.md`.

## Where things are

- `front_end/literaryworm_app/`: the React app (see its `README.md` for routes and layout). Vercel's Root Directory is this folder, so its `vercel.json` (the rewrite that lets every route survive a refresh) lives here too.
- `front_end/BookWorm_web_app_wireframe/`: the Figma Make wireframe. Visual source of truth; don't edit.
- `front_end/style_guide.md`: design tokens, type, components, motion, voice.
- `supabase/`: migrations, Edge Functions (`books`, `manage-profile`, `checkout`, `manage-account`, `stripe-webhook`, `release-emails`, `club-invite`, `author-news`, `dictionary`, `characters`, `whats-new`, `kids-report`, `club-meetings`, `club-digest`, `gift-reminders`, `club-calendar`, `affiliate-click`, `unsubscribe`, `summaries`, `ask`, `quiz`, `recaps`, `discussion`, `natural-voice`), Auth email templates (`templates/`), security tests. See `supabase/README.md`. Project: `literaryworm` (ref `ldzdmrdvmacpudsbngvd`). The app is deployed on Vercel at `https://www.literaryworm.com`; `https://www.literaryworm.com`, `https://literaryworm.com` and `http://localhost:5173` must all be in the `ALLOWED_ORIGINS` function setting, or the browser blocks the functions' answers and the app reports "offline".
- `schema.sql`: generated from the migrations by `supabase/build-schema.sh`; don't edit by hand. `drawsql.png` is its ERD, rendered from `docs/erd/erd.html`.
- `prompt.md`: the build brief and phase plan.
- **Supabase CLI v3** (3.0.0 or later): commands that can run locally target the local stack unless given `--remote` (the linked project) or `--remote=<ref>` (another project or a branch, such as dev `xjvisabdztxvnsglysdh` or production `ldzdmrdvmacpudsbngvd`); `--linked` and `--project-ref` are deprecated (except `supabase link --project-ref`). Every change to a hosted project needs `--yes` when not in a terminal (`db query -f`, `functions deploy`, `storage cp`/`rm`, `db push`); read-only checks use `db query --read-only`, which needs none.
- `docs/releasing.md`: how a change reaches the live site, dev first (the `dev` branch, the Supabase dev branch `literaryworm-dev`, ref `xjvisabdztxvnsglysdh`, and the dev preview), then main through `scripts/promote.sh`.
- `vite-project/`: an unrelated earlier scaffold. Don't use it.

## Commands (run in `front_end/literaryworm_app`)

```bash

npm run lint    # oxlint; must be clean
npm test        # Jest unit tests (src/lib/*.test.ts); must pass before every commit
npm run test:e2e  # Jest + Playwright smoke tests (e2e/*.e2e.ts) on the demo; must pass before every commit
```

## Conventions

- TypeScript strict. React Router DOM, declarative routes with `BrowserRouter`; routes live in `src/App.tsx`.
- **State is in memory only** (`src/store`). No `localStorage`, with two exceptions: the Supabase session (`src/lib/supabase.ts`, key `literaryworm-session`) so a member stays signed in, and which device this browser is (`src/lib/deviceId.ts`, key `literaryworm-device`: a random id and the account id, removed at sign-out) so a refresh isn't a new device. (Termly's consent banner keeps its own `TERMLY_API_CACHE` entry.) Everything else resets on refresh on purpose.
- **Real accounts go through `src/lib/accountApi.ts`** (Supabase Auth, `library_items`, `logs`, the `checkout` function) and `src/lib/useAuthSync.ts` (restores the session, follows sign-in and sign-out). Use `useLibrary()` for the library: it writes to Supabase first, then updates the store. The demo household stays in memory and never calls Supabase.
- **Book lists go through `src/lib/booksApi.ts`**, which calls only the `books` Edge Function. Never fetch Google Books from the browser. In the functions every Google call goes through `callGoogleWithKeys()` with `googleKeys()` (`_shared/googleBooks.ts`): `GOOGLE_BOOKS_API_KEY`, then the fallbacks `GOOGLE_BOOKS_API_KEY_1_AMILLAGE`, `_1_ALICEMILLAGE`, `_1_ROSEZULEIKA`, `_1_ALICESUCC` and `_1_FEMSHEP` (`KEY_SECRETS`, in that order), the next tried when one is rate-limited, refused (403, or a 400 about the key), failing (5xx) or too slow, and no new key started after 15 s; a not-found answers at once. Logs name a key's position, never the key. Kids profiles use the sample catalog only. **Open Library** (`_shared/openLibrary.ts`, `callOpenLibrary()` with `USER_AGENT` naming hello@literaryworm.com): `source=openlibrary` on `home` / `genre` (`genreQuery(g, true)` when `openLibraryFor(ageRating)`, adult profiles only: Open Library has no maturity rating, so works filed as erotica, `MATURE_SUBJECT`, are dropped) asks Open Library first and Google if it fails or is empty; its books have ids `ol-OL…W` (`isOpenLibraryId()`), whose details `mode=volume` and `summaries` fetch from Open Library (`openLibraryDetail()`), credited *Details from Open Library* (`sourceName` in `lib/bookDetail.ts`); its data is CC0, kept a day (`OPEN_LIBRARY_KEEP_SECONDS`) in the same cache tables. The Privacy, Cookie, Terms and Help pages say so (6677). Google's answers are kept briefly in Supabase (`_shared/bookCache.ts`, `google_books_volumes` and `google_books_lists`, service role only, migrations 6666, 6669–6670): each row's `expires_at` is what Google's cache headers allow (`cacheSeconds()` in `_shared/googleBooks.ts`: nothing for no-store, no-cache, private or no lifetime) capped at 7 days (`CACHE_MAX_SECONDS`, also a table check), because the Google APIs Terms (5(e)) forbid keeping copies longer than the cache header permits or permanently; expired rows are never served (no stale fallback) and pg_cron deletes them hourly; the function's own browser `Cache-Control` is capped the same way; empty pages are never kept; a cache failure never fails the request. Members' *Keep discovering* runs on into the other genres (`useBookFeed(query, rating, then)`, `genresAfter()` / `genreOrderAfter()` in `lib/feedChain.ts`), says which it has reached (`stepLabels`, from the hook's `loadedStep`), offers *Back to top of the feed* from `BACK_TO_TOP_AFTER` books, and skips drawing tiles far off screen (`.catalog-grid-endless`, `content-visibility: auto`); a visitor's public home shows `VISITOR_SAMPLE` books, then the log-in invitation (`BookFeed` `sampleSize` / `sampleEnd`).
- **Public logs come from `src/lib/logsApi.ts`** (the `logs` table with the publishable key, embedding only `profiles.display_name`). Public pages never read `library_items`.
- **Reading progress and bookmarks go through `src/lib/useReading.ts`.** Opening a book adds it to the library as Reading; the place is dispatched straight away and saved to Supabase (`reading_progress`) a moment later, so reading never waits for the network; bookmarks save first, then show. Real accounts keep them in `state.accountReading`, in-memory accounts in `ProfileData`; `activeReading()` picks the right one. Positions are fractions of the whole book (`src/lib/reading.ts`), shared by the reader and the player.
- **Household profiles go through `src/lib/useProfiles.ts`.** Real accounts save name, avatar and genres to `reader_profiles` directly; Kids profiles, PINs, limits, age ratings and deletes through the `manage-profile` function (which re-checks the password); PINs are verified on the server. After a change the profiles are read back (`setProfiles`). A real profile has `hasPin`, never the PIN.
- **Account changes go through `src/lib/useAccount.ts`**: membership (pause, resume, cancel, restart) and deleting through the `manage-account` function; display name and marketing emails straight to their tables; Download my data builds a JSON file in the browser.
- **Highlights and notes go through `src/lib/useHighlights.ts`**, like bookmarks: real accounts save to `highlights` first, then show; in-memory accounts keep them in `ProfileData`. A highlight is found by chapter, page and character offsets in the page's text (`src/lib/highlights.ts`). Twelve colours (`HIGHLIGHT_COLORS` in `lib/highlights.ts`, the `highlight_color` enum, and a `--mark-*` and `--paper-*-mark-*` token per colour); a new colour needs all three and an enum migration.
- **Authors and narrators** have pages at `/authors/:name` and `/narrators/:name` (`pages/Person.tsx`, helpers in `lib/people.ts`), keyed by the name shown on the book; link to them with `personPath()`. An author's Google Books titles come from the `books` function's `author` mode. Following goes through `lib/useFollows.ts` (per profile, `follows`, saved first like favourites; loaded with the collections); Home's *New from people you follow* row uses `fromFollowed()`; My Library → *Following* lists them (`components/FollowingView.tsx`). A person's page shows how many profiles follow them from the `follower_count()` RPC (`lib/followersApi.ts`, a count, never who; visitors too), and an author search's *Authors* cards from `follower_counts()` (`fetchFollowerCounts()`, one call for the list, at most 50 names; `followersShort()`). Home's *Most-followed authors* (`components/MostFollowed.tsx`, not Kids) reads `most_followed()` (`fetchMostFollowed()`: names with two or more followers, counts only).
- **Remind me** (`components/RemindMe.tsx` on the book page, `lib/useReminders.ts`, dates in `lib/release.ts`): per profile in `release_reminders` (saved first, loaded with the collections), only for books whose release day is still to come and only when Google gives the exact day. Once the day passes, `components/RemindersView.tsx` shows it on Home (*Out now*) until dismissed, and in My Library → Reminders. Members also get an email that day (see Email) unless they turned it off in Account → Preferences (`account_private.release_emails`, `setReleaseEmails()`).
- **The notification bell** (`components/NotificationBell.tsx` in the header, `lib/useNotifications.ts`, counting in `lib/notifications.ts`): released reminders newer than `ProfileData.notificationsSeenAt`, plus unread club posts up to the reader's chapter (`spoilerFreeUpTo()`; clubs with alerts on; never Kids profiles). Opening it marks the profile seen: members through `mark_notifications_seen()` (the database's time, so every device agrees), the demo in memory. Club posts keep their own read state (`club_members.last_read_at`). New kinds of notification get a count in `bellCount()` and a group in the panel; one with a start time goes in its `alerts` (new until the bell is opened after it), like the goal and streak alerts (`goalAlerts()` in `lib/goals.ts`), the yearly renewal reminder and the yearly offer (`yearlyOffer()` in `lib/billing.ts`: monthly members billed through Stripe, for 30 days from 11 months after `Account.memberSince`, which is `subscriptions.created_at`).
- **Notifications on a device** (Web Push; `lib/push.ts`, rules in `lib/pushState.ts`, *Notifications on this device* in Account → Preferences, members only, production builds only): the browser subscribes with `VAPID_PUBLIC_KEY` (public; the same in `_shared/webpush.ts`) and `save_push_subscription()` keeps it in `push_subscriptions` (never written from the browser directly). The release-emails run sends release-day notifications through `release-emails/push.ts` and `_shared/webpush.ts` (Web Crypto only; keep its RFC 8291 test passing), with the `VAPID_PRIVATE_KEY` function setting; `public/sw.js` shows them. Logging out turns them off on that device (`forgetPushOnSignOut()`). Kinds (`account_private.push_kinds`, `PUSH_KINDS` in `lib/pushState.ts`): release, meeting, club_posts, streak (evening on the device's clock, `push_subscriptions.time_zone`) and request; each is claimed once (`claim_*_pushes()`) and sent by the hourly release-emails run (`release-emails/more.ts`), except request, which manage-profile sends with `notifyAccount()` (`_shared/pushAccount.ts`). A new kind needs its own claim, a `push_kinds` value, a Preferences label and the Privacy Policy's list kept true; club posts never past the reader's chapter.
- **The family shelf** (`lib/familyShelf.ts`, `lib/useFamilyShelf.ts`, `components/FamilyShelfButton.tsx` on the book page, *The family shelf* row on Home): per account in `family_shelf` (up to 100, catalog books; only grown-up and teen profiles add, a trigger checks `added_by`), saved first; the demo keeps a sample in memory. Show it to a profile only through `shelfFor()`, which keeps Kids profiles to what `mayOpen()` allows.
- **Favourites, ratings, custom lists and recent searches go through `src/lib/useCollections.ts`.** They belong to the active profile (`ProfileData`); real accounts save to `favorites`, `book_ratings`, `custom_lists`, `custom_list_items` and `reader_profiles.recent_searches` first, then dispatch (recent searches save in the background). `useAuthSync` loads every profile's collections after the profiles. Shared lists are read with the `shared_list` RPC (`src/lib/sharedListApi.ts`), never the tables.
- **Definitions come from `src/lib/dictionaryApi.ts`**, which calls only the `dictionary` Edge Function (the Free Dictionary API is asked on the server).
- **Audiobook playback lives in `src/components/PlaybackProvider.tsx`** (read it with `usePlayback()` from `src/lib/playback.ts`), above the routes, so a book keeps playing in the mini-player (`src/components/MiniPlayer.tsx`) while the member browses. The player page is a view of it. Opening the reader pauses it; switching profile or signing out stops it, and its last save still goes to the profile that was listening (`saveProgress` / `addTimeUsed` take a `profileId`).
- **The player page and the mini-player have the same controls**, from `usePlayerControls()` (`src/lib/usePlayerControls.ts`; where each control goes is worked out in `src/lib/playerNav.ts`) and the shared pieces in `src/components/PlayerControls.tsx` (volume, *Go to*, player settings, *Listen on another device*, the handoff prompt, *15 more minutes* after the sleep timer). Add a control to both. The sleep timer fades out and Play goes back after it (`sleepVolume()`, `resumeAfterSleep()` in `lib/reading.ts`). Speed, volume, mute, skip lengths and intro and outro skipping are `ProfileData.player`, changed through `usePlayerSettings()`, which saves members' settings to `reader_profiles` in the background; the engine applies them (narrators have `setVolume`).
- **A speed per book** (`lib/bookSpeed.ts`: `speedFor()`, `hasOwnSpeed()`, `withBookSpeed()`, `speedPatch()`, `parseBookSpeeds()`, `BOOK_SPEEDS_MAX` 200): `PlayerSettings.bookSpeeds`, members' `reader_profiles.book_speeds` (jsonb, migration 6731), saved with the other player settings. `usePlayerSettings(bookId)` gives `player.speed` as the open book's own speed and sends a speed change to that book when it has one; *Keep this speed for this book* in `PlayerSettingsDialog` (`ownSpeed`, `setOwnSpeed`). Anything reading the playing speed uses `speedFor(player, book.id)` (PlaybackProvider, MediaSession, ListenAlong, Club). What's new 6732.
- **Listen on another device** is for members: `src/lib/useDeviceLink.ts` registers this browser as a `listening_devices` row (one per browser, the id kept by `deviceIdFor()`) (checking in through `touch_listening_device()`), and `src/lib/devicesApi.ts` sends and hears `playback_handoffs` (Supabase Realtime, plus a check when the tab comes back). It reaches the views as `usePlayback().link`; `open(book, { at, autoplay })` opens a book at a place.
- **Lock screen:** `components/MediaSession.tsx` (above the routes) puts the open book in the Media Session API with the same actions as the mini-player; artwork is drawn by `lib/coverArt.ts` (also used by quote cards, `lib/quoteCard.ts`). **Install:** `public/manifest.webmanifest` and `public/icons`; `lib/installApp.ts` keeps the browser's install offer (imported first in `main.tsx`).
- **Stats** (`lib/stats.ts`, My Library → Stats) come from `ProfileData.readingDays`: `listened` is the listening part of `seconds`, `books` the ids finished that day. Members save both through `record_reading(profile, day, minutes, finished, listening_minutes, volume_id)` (`reading_days.listening_minutes`, `finished_books`). Pass `listening` to `useDailyLimit` for player time and the book id to `finishedBook`. **Stats by book** (`lib/bookStats.ts`, `components/BookStatsSection.tsx` on the book page, *Your time with this book*): pass `track` to `useDailyLimit` (book id and place, 0–1) so time also counts towards that book: `ProfileData.bookDays` in memory, members' through `record_reading(..., p_fraction)` into `book_reading_days` (per profile, book and day), read by `useBookDays()`. *Share as a picture* draws the year as a card (`lib/yearCard.ts`, `components/YearCardDialog.tsx`) and *Play as a story* as 1080 × 1920 screens (`lib/yearStory.ts`, `components/YearStoryDialog.tsx`); it and the quote card share `components/ShareImage.tsx` (look, preview, Share, Download, Copy), and both are drawn in the browser, never uploaded.
- **Recommendations** are worked out in the browser (`lib/recommend.ts`) from a profile's finished books, ratings and favourites; only catalog titles the profile may see, never books in its library.
- **Club notifications and listen along** use Supabase Realtime: `components/ClubAlerts.tsx` listens to `club_posts` once and passes posts on through `lib/clubEvents.ts`; `components/ListenAlong.tsx` keeps playback and `club_listening` in step for the session in `lib/listenAlong.ts`. *Where everyone is* on a club's page (`components/ClubPlaces.tsx`) reads `club_places()` (members only, and only members who turned on `club_members.share_place`); never read other accounts' `reading_progress` any other way. Never alert about, or count, posts past the reader's chapter (`spoilerFreeUpTo()` in `lib/clubs.ts`). Give every Realtime channel its own name (channels sharing one close together).
- **Billing is Stripe** (`supabase/functions/_shared/stripe.ts`): a new membership is paid on Stripe Checkout (hosted, so card details never reach us); `checkout` returns its url and only the `stripe-webhook` function writes a paid membership, mapping events to accounts through `stripe_customers` and handling each once (`stripe_events`). Prices are found by lookup key (`literaryworm_<plan>_monthly`, and `literaryworm_<plan>_yearly` at ten times as much): Basic $30.00, Standard $40.00, Premium $60.00 a month (Premium in migration 6713, Basic and Standard in 6706; before that $15, $20 and $30, 6585). To change a price, create a new Stripe price on the same product that takes over the lookup key (`transfer_lookup_key`) and archive the old one (running memberships keep it; the Terms promise notice before a member's price changes), then change `data/plans.ts`, `PRICES` in `checkout/index.ts` and `public.plans` (a migration) together, and rewrite the description in `index.html` from `lib/seo.ts` (prices in the description; `seo.test.ts` fails until they match). **Structured data** (`lib/seo.ts`): `index.html` carries only what's true on every page (WebSite with its search, Organization); pages add their own with `components/StructuredData.tsx`: every public page a node from `pageData()` (its WebPage type, `@id` its address + `#webpage`, `isPartOf` the WebSite, a BreadcrumbList from `HOME_CRUMB`, and a `mainEntity`): Home and Plans (`mainEntity` the membership, `MEMBERSHIP_ID`), Search (SearchResultsPage when searching), Sign up, What's new (CollectionPage with the latest entries), each policy (`dateModified` from its update), authors, narrators and public readers (ProfilePage, `personNode()`), series (CollectionPage plus a BookSeries from `seriesData()`) and book pages (ItemPage, trail through the series; catalog books point at their Book with `bookRef()`); never uploads, members-only pages, clips or shared lists. Plus the membership Product with each plan's monthly and yearly Offer (no returns) and the FAQPage on Home and Plans, and a Book (ebook and LibriVox audiobook) on each LiteraryWorm title's page. A new public page gets its `pageData()` node. Every page's `<link rel="canonical">` and `og:url` are set by `components/Canonical.tsx` from `canonicalUrl()` (the path on `www.literaryworm.com`, no query or trailing slash); never put a fixed canonical in `index.html`, which every route is served. `public/sitemap.xml` lists the public pages (built by `scripts/build-sitemap.py` from the catalog, series and footer pages, each footer page dated by its `updated`: run it after adding any; `robots.txt` disallows the members-only routes; keep `llms.txt` and `humans.txt` true to the prices and stack). **Yearly billing** (`subscriptions.billing_interval`, from the price's lookup key; `Account.billingInterval`, `renewsAt`): a year starts the day it's paid for; monthly to yearly switches in place (`billing_cycle_anchor: { type: "now" }`, an object since API version 2026-09-30, the unused month credited), yearly moves up at once (the difference charged) and down at renewal, and to monthly at renewal through a Stripe subscription schedule (`scheduleMonthly()` in `_shared/stripe.ts`: the year as it is, then the monthly price; the schedule's phase sets the subscription's `switch_to_monthly` metadata, which `subscriptionRow()` reports as `subscriptions.switch_to_monthly` only while the schedule is attached; choosing yearly again or cancelling calls `releaseSchedule()`, and anything that cancels a Stripe subscription must release its schedule first); yearly memberships can't pause or move their billing day; a late cancel ends a year on; the bell reminds 30 days before renewal (`renewalReminder()` in `lib/billing.ts`, which the Terms promise). Pause, cancel, billing day and the payment method (Customer Portal) go through `manage-account`, which changes Stripe first. **A first membership starts with a free week** (`FREE_TRIAL_DAYS` 7 in `checkout/handler.ts` and `data/plans.ts`): checkout passes `trial_period_days` only when the account has never had a `subscriptions` row (never staff, never gifts), with `free_trial` in the subscription's metadata; `subscriptionRow()` keeps its end in `subscriptions.trial_until` while it lasts (6708), Account shows it as the first charge and hides the billing-day change, Plans shows *First 7 days free* and the trial terms; referral and affiliate rewards wait for the first real payment (they skip $0 invoices). The Terms (section 5), Return Policy, Help, the FAQ and `index.html`'s description say so (6709). **Cancelling needs 48 hours' notice** to stop the next charge (`cancellationEnd()` in `_shared/stripe.ts` and `lib/billing.ts`, the same rule): later than that, Stripe's `cancel_at` is set a period on and the membership ends after one more charge; `subscriptions.cancel_at` is when an ending membership ends (the webhook keeps it from Stripe). No refunds. Keep the Terms, the Return Policy, the Plans renewal terms and Account's billing section saying so. Billing history and promo codes (`components/BillingHistory.tsx`) also go through `manage-account` (`billing_history`, `promo_code`): read from Stripe each time, never copied to the database; Checkout allows promotion codes. Receipt links are Stripe's hosted invoice pages. **Gift memberships** (`pages/Gifts.tsx` at `/gifts`, `components/RedeemGift.tsx` in Account, Plans and Gifts, `lib/gifts.ts`): `checkout` with `{ gift: true, planId, months, startsOn? }` opens a one-off Checkout (the plan's own product and monthly price × months, or its yearly price for 12 months, two months free, as `giftPriceCents()` in `lib/gifts.ts` shows; so it's taxed like the membership; no `custom_text`, which Stripe Managed Payments refuses); `stripe-webhook` makes the code in `gift_codes` once per session (with `starts_on` from the session's metadata: a gift bought for a later day, up to a year ahead, `parseGiftStart()`; it can't be redeemed before that day starts anywhere, `giftStarted()`; the buyer is emailed three days before a later start by the `gift-reminders` function, hourly pg_cron, `claim_gift_start_reminders()`, `gift_codes.reminded_at`, never with the code; or, when the buyer gave `recipientEmail` (and an optional `message`, `GIFT_MESSAGE_MAX`), the same function emails the code to that person once it can be redeemed, `claim_gift_deliveries()`, `delivered_at`, and then clears the address and message, and there's no buyer reminder); `manage-account` `gift` redeems it once (claim first, released only if Stripe fails): on a membership on the same plan the next charge moves back (`trial_end`), without one Stripe starts a subscription free until then that cancels if no card is added, carrying `gift_consent_at`, and the webhook writes the membership from that consent. **Gift wishlists** (`lib/wishlist.ts`): every shared list is a wishlist; `pages/SharedList.tsx`'s *Give this list as a gift* opens `/gifts?books=&for=` (`wishlistGiftPath()`), which Gifts reads with `readWishlistParams()` (catalog ids only, at most 10, the owner's name) to start the picker; nothing new is stored, and checkout checks the books again. A gift can come with up to 10 catalog books (`books` on the checkout call, `GIFT_BOOKS_MAX` and `addGiftBooks()` in `lib/gifts.ts`, `components/GiftBooksPicker.tsx` on Gifts: find a title or add one of your lists; `parseGiftBooks()` in `_shared/stripe.ts` checks them against `_shared/catalog.ts` in `checkout` and again in `stripe-webhook`, which reads the comma-joined `books` metadata into `gift_codes.books`, migration 6574); `claim_gift_deliveries()` returns them so the recipient's email names them, and `manage-account` adds them to the redeemer's library as Want to read after redeeming (a failure there is only logged), after which `RedeemGift` reloads the library (`setAccountLibrary`). `subscriptions.gift_until` (from the subscription's metadata) shows in Account and blocks billing-day moves. Never send Stripe's ids to the browser (`subscriptions.stripe_linked` says whether a card is on file), never pass `payment_method_types`, and keep keys in function secrets (`STRIPE_SECRET_KEY`, a restricted `rk_` key, and `STRIPE_WEBHOOK_SECRET`).
- **Refer a friend** (`lib/referrals.ts` for the rules, `REFERRAL_MONTHS_MAX` 2; `lib/referralsApi.ts`; `components/ReferAFriend.tsx` in Account → Plan and billing; *A friend invited you* on Sign up from `/signup?ref=`): `referral_codes` (one per account, `my_referral_code()`, never for staff) and `referrals` (migrations 6657–6660), noted at sign-up by `private.record_referral()` on `auth.users` from `raw_user_meta_data.referral_code` (`signUp({ referralCode })`). On the friend's first paid invoice (or a paid Checkout), `stripe-webhook` calls `claim_referral_reward()` once, which says what to credit: a month of each member's own plan (`plans.price_cents`) as a Stripe customer balance credit (`createBalanceTransaction`, idempotency key per referral and side), the inviter at most 2 in all (locked per inviter) and never staff; a failure hands it back (`release_referral_reward()`) so Stripe's retry tries again. No coupons. The inviter sees counts only (`my_referrals()`), the friend their own row; Stripe ids stay server-side. Keep the Terms (30. Membership) and Privacy Policy saying so (6659).
- **Before you cancel** (`lib/cancelSurvey.ts` for the reasons, `saveOfferFor()` and `planBelow()`; `components/CancelDialog.tsx` in Account → Plan and billing; `_shared/cancelReasons.ts` on the server, kept in step by `cancelSurvey.test.ts`): Cancel membership asks why (optional: 7 reasons, a note up to 500 characters, needing a reason), then offers the one thing that fits (pause on monthly billing, the plan below, uploads, Help, or the month's credit) beside the usual confirmation, and *Cancel anyway* always works. `manage-account` keeps the answer in `cancellation_feedback` with `cancel` (`outcome` cancelled) or `cancel_feedback` (kept; never stops the cancel if it fails), service role only, a year (pg_cron), migrations 6715–6718. The month's credit (`save_offer_check`, `save_offer`): once per account (`save_offer_credits`, claimed first, handed back if Stripe fails), a month of the plan (`plans.price_cents`) as a Stripe customer balance credit (`save-offer-<account>` key), only for a membership paid through Stripe now (`creditEligible()`: not a free week, a gift, paused, ending or staff). ## Phase workflow

Build in phases (see `prompt.md`). At the end of each phase:

1. `npm run build`, `npm run lint`, `npm test` and `npm run test:e2e` clean (GitHub Actions runs all four on every push to `dev` and `main`, `.github/workflows/ci.yml`). A new page or flow gets a smoke test in `e2e/smoke.e2e.ts`. New logic in `src/lib` gets tests beside it (`*.test.ts`). The paging snapshots in `src/lib/__snapshots__` must not change unless paging is meant to (saved highlights depend on it).
2. Playwright screenshots at 1440px and 390px, compared against the wireframe; save keepers to `front_end/literaryworm_app/docs/screenshots/`.
3. Chrome DevTools: no console errors; Lighthouse accessibility 100.
4. Update `schema.sql` and re-render `drawsql.png` for any new data.
   **Always fix and update the website's schema and the sitemap too**, with every change:
   - The schema.org structured data (`lib/seo.ts`, `components/StructuredData.tsx`, `index.html`): keep it true to each page and to the app (prices, features, the plans' offers, book pages), with nothing an address doesn't show, and fix anything Google's Rich Results test would flag (missing required fields, wrong types). Keep `seo.test.ts` and the smoke test passing.
   - The sitemap (`public/sitemap.xml`): run `scripts/build-sitemap.py` after any new or removed public page, catalog title or series, check it lists only public, indexable pages (never members-only routes, which `robots.txt` disallows, or one-off links like `/clips/…`), and keep `robots.txt` pointing at it.
5. Update the docs (app README phase table, `user_stories.md` build status, `user_journey.md` build notes, root `README.md` project status).
6. Commit only the files for that work on `dev`, apply its migrations to the Supabase dev branch first, push `dev`, and stop for the user's review. Production migrations, function deploys and `scripts/promote.sh` (which moves `main` to `dev` only when every test and dev's CI pass) follow `docs/releasing.md`, with the user's approval.

## Rules that must not be broken

- Always fix and update the website's schema (the schema.org structured data in `lib/seo.ts`, `components/StructuredData.tsx` and `index.html`) with every change, so it stays true to each page and the app; and fix and update the sitemap (`scripts/build-sitemap.py`). See step 4 of the phase workflow.
- Never commit secrets. `.env*` files stay local; only `.env.example` (no real values) is shared. Never put a secret in a `VITE_` variable.
- The browser must never call Google Books directly (backend phases: go through a Supabase Edge Function).
- Don't edit, delete or rewrite anything in `prompt-records/` or the hooks in `.claude/hooks/`.
- Every Supabase table has Row Level Security enabled, with `(select auth.uid())` policies and column-level grants. The Edge Functions' `service_role` needs its own grants: migration 6636 grants it every public table, sequence and function and makes that the default, because newer branches (the dev branch) don't grant it otherwise; check a new table with `has_table_privilege('service_role', …)` on the dev branch. Index every foreign key, with `CREATE INDEX CONCURRENTLY` in its own one-statement migration (the MCP `apply_migration` runs in a transaction, so apply those with `execute_sql`).
- Edge Functions validate every input, use the CORS allowlist in `_shared/cors.ts`, and return `{ error: { code, message } }`. Test (`deno check`, `deno test`) before deploying.
- `DELETE` statements always have a `WHERE` clause (a hook blocks the rest).
- Don't stage unrelated files (`.cto-toolkit/`, tool folders like `.windsurf/`, `prompt-records/` edits made by hooks) in feature commits.
